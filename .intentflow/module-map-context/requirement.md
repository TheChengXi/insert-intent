# 需求文档：会话上下文模块地图注入（module-map-context）

## 项目意图
在每个新工作会话的第一个步骤开始时，将当前工作区 `.intentflow/_packages/` 顶层所有 `*.yml` 模块文件的**原文**拼接后，注入到会话上下文的最顶端（作用类似 AGENTS.md）。这样模型无需扫描整个目录树就能获知各模块的职责、入口、依赖与分组文件地址，节省理解成本与 token，也省去人工解释模块用途。

> **本迭代交付形态**：仅产出需求 + 实现方案文档，不写代码。代码留待后续设计/执行阶段落地。

## 功能清单
1. 会话首步注入模块地图
2. 工作区自适应（无 `_packages` 时优雅跳过）
3. yml 原文拼接（不定制/不解析内容）

## 核心功能

### 核心功能1：会话首步注入模块地图
- **能力**：系统能够在每个新工作会话的第一个符合条件的步骤（`agent/pre-step`）开始时，一次性读取当前工作区 `.intentflow/_packages/` 顶层的全部 `*.yml` 文件，将拼接结果作为持久上下文快照注入该步骤批次的最顶端。
- **业务价值**：模型首轮即掌握模块地图，无需自行扫描目录即可理解项目结构，节省 token 并消除结构解释成本。

### 核心功能2：工作区自适应（优雅跳过）
- **能力**：系统能够判断当前工作区是否存在 `.intentflow/_packages/`；不存在（或缺省/空）时正常继续会话，不注入、不报错。
- **业务价值**：同一插件在无该约定目录的工作区也能安全装配，不影响其它工作区使用。

### 核心功能3：yml 原文拼接
- **能力**：系统能够将各模块 yml 文件的内容**逐字逐行**拼接注入，不做内容改写、不做结构解析、不加额外引导头。
- **业务价值**：注入内容与维护者在 yml 中写的一致，语义由维护者完全控制，最大程度降低误读与实现复杂度。

## 业务规则

### 注入时机（每会话一次）
- **场景**：每个新工作会话的首个步骤。
- **行为**：在首个符合条件的 `agent/pre-step` 进入非空批次时，系统读取 `_packages/*.yml` 并拼接为一个持久上下文快照，注入该批次的最顶端（位于首条用户消息之前）。
- **异常处理**：若首步被拒绝或批次为空，则基线留待本会话后续步骤首次进入时补入（同一会话内只完成一次，不重复累积）。

### 注入位置
- **场景**：任何一次有效注入。
- **行为**：拼接结果处于会话上下文的最顶端，优先于其它消息，作用上等同 AGENTS.md 型的基线上下文。
- **异常处理**：无——位置固定，不随内容变化。

### 扫描深度
- **场景**：读取 `_packages` 目录时。
- **行为**：仅读取 `.intentflow/_packages/` **顶层**的 `*.yml` 文件；不递归子目录。
- **异常处理**：目录不存在 → 跳过；顶层无 `*.yml` → 跳过；个别文件读取失败 → 跳过该文件，不阻塞其余文件。

### 内容与顺序
- **场景**：拼接多个 yml 文件时。
- **行为**：每文件内容原样保留（含缩进与注释），按文件名排序（如字典序）确定拼接顺序，确保在同一工作区下顺序稳定。
- **异常处理**：yml 语法不合法不作校验——因采用原文拼接，不解析，故不产生解析错误。

### 跨会话/压缩行为
- **场景**：会话被压缩（context compaction 遮蔽基线）或会话被恢复（resume）。
- **行为**：不重新注入——仅新会话的首个步骤注入一次，之后无论是否被压缩/恢复都不再补入。
- **异常处理**：无——按此规则不重复注入。

## 预设测试

> 从用户视角可执行的测试步骤，验证功能是否符合预期。

### 前置条件
- 工作区存在 `.intentflow/_packages/`，内含 ≥1 个 `*.yml`，内容符合给定模块格式。
- DSH 装配了本插件并按本方案开启。

### 测试步骤
1. **[启动新会话]**：在含 `_packages/*.yml` 的工作区启动一个新的工作会话并发出第一条用户消息。
   **预期结果**：会话上下文最顶端出现各模块 yml 的**原文拼接**（含每文件的 packageName、summary、groups、files），顺序稳定且位于首条用户消息之前。
2. **[验证免扫描理解]**：不提前查看目录，仅基于会话上下文追问"每个模块入口/依赖是什么"。
   **预期结果**：模型能直接作答，说明模块地图已生效、无需扫描即可理解结构。
3. **[压缩后不重复]**：让上下文被压缩或恢复会话后继续操作。
   **预期结果**：模块地图不再重复注入（仅原首个步骤的一次基线；若被遮蔽则后续不再补入）。
4. **[内容原样]**：对比注入文本与源 yml 文件内容。
   **预期结果**：逐字一致，无额外引导头、无改写。

### 异常场景
- **[无 `_packages` 目录]**：启动会话 → 不注入任何模块内容，会话正常运行，无报错。
- **[`_packages` 为空]**：启动会话 → 不注入，无报错。
- **[yml 语法非法]**：注入非法 yml → 仍以原文注入原文本（不进解析、不抛解析错误）。

## 边界收束

**此时必做**：
- 每新会话首个步骤注入一次、位置在上下文最顶端。
- 仅读 `.intentflow/_packages/` 顶层 `*.yml`，文件名排序拼接原文。
- 缺目录/空目录优雅跳过。

**此时不做**：
- 递归扫描子目录 — 无需此需求，待出现嵌套结构再扩展。
- 压缩/恢复后补注入 — 用户明确只需新会话首步一次，保持"省 token"目标最小化。
- yml 校验/结构化解析 — 原文拼接已满足目标，解析增加复杂度且要求注入头部改写，留待需要结构化展示时再做。
- 会话中途监听文件变更并增量更新 — 超出"会话开始注入"的目标，待需实时同步时再做。
- 代码实现 — 本迭代仅文档，代码留待后续。

## 实现对齐

> 锚定实现路径前已核对现状：目标插件参照 DSH 现成的两种注入机制（`dsh-agent-instructions` 的 AGENTS.md 基线注入、`dsh-time-context` 的 sourced 上下文快照注入）推导路径。当前工作区 `.intentflow/_packages` 尚不存在，本需求以"约定目录若存在则注入，否则跳过"为基线。

- **[会话首步注入]**：新增一个 DSH 插件，注册 `agent/pre-step` 监听；首个符合条件的进入步骤，用 `ctx.fs` 读取工作区根 `.intentflow/_packages/*.yml`，拼接后构造一条 sourced `user/message` 上下文（如 `kind: 'module-map-context'`、`form: 'snapshot'`），折入该步骤批次的最顶端并进入持久历史。
- **[工作区自适应]**：注入前用 `ctx.fs` 探测 `.intentflow/_packages` 是否存在及是否含顶层 `*.yml`；缺省即跳过，不注入、不报错。
- **[yml 原文拼接]**：按文件名排序，将每个文件内容逐字拼接（不解析、不校验、不加引导头）。
- **[装配与生效面]**：插件装配到 `dsh` 的 web/headless profile（`dsh.profile.bundles` 或 `cordis.patch.yml`），作用于其覆盖的工作区。

**推导出的约束**（本迭代交付形态为仅文档，以下为设计阶段需确认的假设，标注待确认）：
- 注入为持久上下文快照，进入历史而非瞬时注入；首步之后不重复、不被压缩后再补。— 假设-确认
- 读取经 `ctx.fs` provider（与 `dsh-agent-instructions` 一致），无 provider 的装配不注入也不报错。— 假设-确认
- 拼接顺序用文件名排序求稳定，而非默认目录返回序。— 假设-确认

**design 决策**（方案比较类，交由 design 阶段选择）：
- 注入格式走 `time-context` 式 `snapshot` 快照 vs `agent-instructions` 式 `instructions` 基线框各的取舍（是否自带可被模型感知的说明文案）。
- 插件命名与装配粒度（独立 bundle 注入 web profile vs 覆盖既有 agent-instructions）。
- 字节预算（顶层 yml 总量无预算 vs 设置上限避免超大注入；用户已选"原文拼接"倾向不截断）。
